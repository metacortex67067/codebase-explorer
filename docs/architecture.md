# Архитектура Codebase Explorer

Документ для защиты курсового проекта. Описывает структуру системы,
ключевые проектные решения и их обоснование.

## 1. Общая схема

```
                  +-----------------+
   zip / git URL  |   ingestion     |  фильтрация по типу файла,
        ----->    |   (loader)      |  каппинг размера и кол-ва
                  +--------+--------+
                           | list[SourceFile]
                           v
                  +-----------------+
                  |    parsing      |  AST -> Module, FunctionInfo,
                  |  (python_parser,|       ClassInfo
                  |   dep_graph)    |  + граф зависимостей
                  +--------+--------+
                           | list[Module]
                           v
                  +-----------------+
                  |    indexing     |  нарезка на CodeChunk,
                  |  (chunker,      |  эмбеддинги, ChromaDB
                  |   embedder,     |
                  |   vector_store) |
                  +--------+--------+
                           |
              +------------+-------------+
              v                          v
       +-------------+            +-------------+
       |     llm     |            |     qa      |
       | summariser  |            |  RAG-loop   |
       +------+------+            +------+------+
              |                          |
              +-----------+--------------+
                          v
                  +-----------------+
                  |  api / mcp      |
                  +-----------------+
```

## 2. Принципы

**Слоистость.** Каждый слой знает только о слое ниже. `ingestion` ничего
не знает об AST. `parsing` не знает про эмбеддинги. Это позволяет
тестировать каждый слой изолированно и в будущем заменять реализации
(например, добавить парсер для JS — затрагивается только `parsing`).

**Pydantic как контракт.** Все межслойные данные — это pydantic-модели
из `src/core/models.py`. Они валидируются на границах, сериализуются
в JSON автоматически, и работают как живая документация структуры
данных.

**12-factor конфигурация.** Все настройки — через переменные окружения,
читаются один раз в `src/core/config.py`. Никаких секретов в коде.

**Отказоустойчивость на уровне файла.** Если один Python-файл сломан
(синтаксическая ошибка, битая кодировка), индексация продолжается —
просто этот файл попадает в список `failed`. Курсовая проверяется
на реальных репозиториях, где такое встречается.

## 3. Ключевые решения и альтернативы

### Парсинг через `ast` из stdlib, а не tree-sitter / LibCST

**Почему `ast`:** zero dependencies, стабильное API, точные line numbers,
встроенная поддержка docstrings через `ast.get_docstring`. Для Python
этого достаточно.

**Когда стоило бы tree-sitter:** если бы поддерживали несколько языков
из коробки — у tree-sitter единый интерфейс для C, JS, Go и т.д.
Но для MVP с одним языком это лишняя сложность.

### Локальные эмбеддинги `sentence-transformers`, а не OpenAI Embeddings API

**Почему локально:** (1) бесплатно — не тратит бюджет на API-вызовах,
(2) не зависит от сети на демо, (3) детерминированно. Модель
`all-MiniLM-L6-v2` весит 80 МБ, выдаёт 384-мерные векторы, на CPU
работает достаточно быстро для репозиториев в тысячи функций.

**Когда стоило бы OpenAI:** для очень больших корпусов или когда
важно семантическое качество выше — `text-embedding-3-large` объективно
лучше понимает код. Это рассматривается как future work.

### ChromaDB как vector store

Альтернативы — FAISS, Qdrant, Weaviate. ChromaDB выбран потому что:
- Ставится одной `pip install`, без отдельного сервера.
- Метаданные (модуль, qualified_name, line numbers) хранятся
  рядом с векторами — не нужен внешний key-value.
- Persistence из коробки: индекс сохраняется на диск.

### Anthropic Claude как LLM

Выбран по двум причинам: (1) есть нативная поддержка MCP (требование
задания), (2) Claude Haiku 4.5 — быстрая и дешёвая модель, что важно
для интерактивного Q&A.

### Нарезка кода: по семантическим единицам, не по символам

Чанки = функции и методы целиком + отдельный «module header» чанк
с docstring модуля и сигнатурами. Так каждый чанк представляет
осмысленную единицу кода, и LLM получает связный контекст. Альтернатива
(slicing по 500 символов) портит контекст и даёт хуже точность RAG.

## 4. Тестирование

- **Unit-тесты:** для каждого модуля в `src/`. LLM в тестах мокается,
  чтобы тесты были детерминированными и не требовали API-ключа.
- **Интеграционный тест:** прогон полного пайплайна на синтетическом
  мини-репозитории из `tests/conftest.py`.
- **Тесты API:** FastAPI TestClient прогоняет HTTP-эндпоинты.
- **Целевое покрытие:** ≥70%, замеряется через `pytest-cov`.

## 5. Метрики

Снимаются на репозитории `examples/`:
- Время индексации (медиана, p95).
- Latency REST-эндпоинтов.
- Размер ChromaDB-индекса на диске.
- Точность Q&A на ground-truth наборе из ~10 вопросов (доля ответов,
  цитирующих корректный модуль).

## 6. Что осталось за рамками v1 (future work)

- Поддержка JS/TS/Go через интерфейс `LanguageParser`.
- Облачные эмбеддинги для повышения качества RAG.
- Визуализация графа зависимостей (текущая версия отдаёт только JSON).
- Инкрементальное обновление индекса при изменении файлов.
- Авторизация на API — сейчас сервис рассчитан на локальный запуск.
