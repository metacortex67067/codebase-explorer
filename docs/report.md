# Codebase Explorer — отчёт по курсовой работе

## 1. Введение

Современная разработка всё чаще проходит в условиях, когда инженер
должен быстро разобраться в чужом коде: при подключении к существующему
проекту, при code review больших pull request'ов, при аудите
open-source-зависимостей. Линейное чтение исходников плохо
масштабируется — на проекте в десятки тысяч строк это занимает дни,
а вопросы вроде «где определяется этот класс?» или «что делает этот
модуль на верхнем уровне?» возникают сотни раз.

**Цель работы** — построить сервис, который принимает Python-репозиторий,
строит по нему структурированное представление и отвечает на естественно-
языковые вопросы об архитектуре кода с цитированием конкретных
фрагментов.

## 2. Постановка задачи

Сервис должен:

1. Принимать репозиторий в двух форматах: zip-архив или git URL.
2. Строить AST-представление каждого Python-файла (модули, классы,
   функции, импорты, docstrings).
3. Строить граф внутренних зависимостей между модулями.
4. Индексировать код в векторном хранилище для семантического поиска.
5. Отвечать на вопросы пользователя на естественном языке, цитируя
   конкретные функции/классы, на которых основан ответ.
6. Предоставлять два интерфейса: REST API (для интеграции и веб-UI)
   и MCP (для использования из Claude Desktop / IDE).
7. Обладать тестовым покрытием ≥ 70%.

Скоп v1: только Python; лимит репо 50 МБ / 2000 файлов; локальные
эмбеддинги.

## 3. Обзор существующих решений

| Решение | Что делает | Чем отличается от нашего |
|---|---|---|
| **GitHub Copilot Chat** | Q&A по открытому проекту в IDE | Закрытый, индекс не персистентный, нельзя экспортировать граф зависимостей или summary. Привязан к IDE. |
| **Sourcegraph Cody** | Семантический поиск + LLM Q&A | Корпоративное решение, требует развёртывания индексатора, платное для приватных репо. |
| **Cursor** | LLM-IDE с пониманием контекста | Indexing неявный, RAG неэкспонирован как API — нельзя интегрировать в свои инструменты. |
| **Aider / Continue.dev** | Open-source AI-кодинг | Заточены под редактирование, не под explanation. |

Наш сервис заполняет нишу «explanation-only с открытым API»: мы не пишем
код за пользователя, мы помогаем понять чужой код, и делаем это через
два стандартных интерфейса (HTTP + MCP), чтобы он встраивался во что
угодно.

## 4. Архитектура

### 4.1. Слоистая декомпозиция

```
                 +-----------------+
  zip / git URL  |   ingestion     |  фильтрация по типу файла,
       ----->    |   (loader)      |  каппинг размера и кол-ва
                 +--------+--------+
                          | list[SourceFile]
                          v
                 +-----------------+
                 |    parsing      |  AST -> Module, FunctionInfo,
                 |  (python_parser,|       ClassInfo
                 |   dep_graph)    |  + граф зависимостей
                 +--------+--------+
                          | list[Module]
                          v
                 +-----------------+
                 |    indexing     |  нарезка на CodeChunk,
                 |  (chunker,      |  эмбеддинги, ChromaDB
                 |   embedder,     |
                 |   vector_store) |
                 +--------+--------+
                          |
             +------------+-------------+
             v                          v
      +-------------+            +-------------+
      |     llm     |            |     qa      |
      | summarizer  |            |  RAG-loop   |
      +------+------+            +------+------+
             |                          |
             +-----------+--------------+
                         v
                 +-----------------+
                 |   RepoService   |  единый фасад
                 +--------+--------+
                          |
             +------------+-------------+
             v                          v
      +-------------+            +-------------+
      |  REST API   |            | MCP server  |
      |  (FastAPI)  |            |   (stdio)   |
      +-------------+            +-------------+
```

**Принцип слоёв**: каждый слой знает только о слое ниже. Ingestion не
знает про AST, parsing не знает про эмбеддинги, и так далее. Это даёт
независимое тестирование и возможность заменять реализации (например,
добавить `LanguageParser` для JavaScript — изменится только слой parsing).

### 4.2. Контракт между слоями: pydantic-модели

Все межслойные данные — pydantic-модели из `src/core/models.py`:
`SourceFile`, `Module`, `ClassInfo`, `FunctionInfo`, `CodeChunk`,
`ModuleSummary`, `QASource`, `QAResponse`, `RepoIndex`. Это даёт:

- Валидацию на границах автоматически.
- JSON-сериализацию для API без отдельных DTO.
- Живую документацию структуры данных.

### 4.3. Конфигурация

12-factor через `pydantic-settings`. Все настройки — `storage_dir`,
лимиты, имя модели эмбеддингов, API-ключ Anthropic, имя LLM-модели,
top-K для RAG — читаются из env / `.env` файла один раз в
`src/core/config.py`. Никаких хардкодов в коде.

### 4.4. Отказоустойчивость

- **Сломанный Python-файл** не валит индексацию: парсер возвращает
  `None`, файл попадает в `failed`, остальные продолжают индексироваться.
- **Битая кодировка** — читаем с `errors='replace'`.
- **Сломанный JSON от LLM** — graceful fallback: оригинальный текст
  становится `summary` / `answer`, citations пустые.
- **Отсутствует ANTHROPIC_API_KEY** — индексация всё равно проходит,
  модули получают плейсхолдерные summary `(summary unavailable: LLM
  not configured)`. Граф зависимостей и парсинг работают без LLM.

## 5. Ключевые проектные решения и альтернативы

### 5.1. AST из stdlib, а не tree-sitter / LibCST

**Почему `ast`**: zero dependencies, стабильное API, точные `lineno` /
`end_lineno`, встроенная поддержка docstrings через `ast.get_docstring`.
Для Python этого достаточно.

**Когда стоило бы tree-sitter**: если бы поддерживали несколько языков
из коробки — у tree-sitter единый интерфейс для C/JS/Go/...
Но для MVP с одним языком это лишняя сложность.

### 5.2. Локальные эмбеддинги `sentence-transformers`

**Почему локально**: (1) бесплатно — не тратит бюджет API-вызовов,
(2) не зависит от сети на демо, (3) детерминированно. Модель
`all-MiniLM-L6-v2`: 384-dim, 22 МБ, на CPU работает в реальном времени.

**Когда стоило бы OpenAI**: для очень больших корпусов или когда важно
семантическое качество выше — `text-embedding-3-large` объективно
лучше понимает код. Это future work.

### 5.3. ChromaDB как vector store

Альтернативы — FAISS, Qdrant, Weaviate. ChromaDB выбран потому что:
- Ставится одной `pip install`, без отдельного сервера.
- Метаданные (`module_path`, `qualified_name`, `line_start/end`)
  хранятся рядом с векторами — не нужен внешний key-value.
- Persistence из коробки.

Один общий collection, репозитории изолированы фильтром
`where={"repo_id": ...}` — это даёт линейный код запроса и снимает
вопросы lifecycle отдельных collections.

### 5.4. Anthropic Claude как LLM

Выбран по двум причинам: (1) есть нативная поддержка MCP (требование
задания), (2) Claude Haiku 4.5 — быстрая и дешёвая модель, что важно
для интерактивного Q&A.

### 5.5. Семантические чанки, не slicing по символам

Чанки = функции / методы целиком + отдельный `module_header` чанк
с docstring модуля и сигнатурами. Слайсинг по 500 символам портит
контекст и даёт хуже точность RAG: чанк может закончиться в середине
if-блока, embedding такого огрызка ни о чём не говорит.

Класс генерирует **и** `class`-чанк (весь класс целиком) **и**
по `class_method`-чанку на каждый метод. Дублирование намеренное:
запрос «как реализован Counter.inc» должен попадать в method-чанк;
«что такое Counter в целом» — в class-чанк. Векторный поиск
ранжирует их естественным образом.

### 5.6. Цитирование по индексу чанка, не по `qualified_name`

В RAG-промпте LLM получает пронумерованный список чанков и просят
вернуть ответ + `used_chunk_indices: [int, ...]`. Это надёжнее,
чем просить копировать `qualified_name`: модель может перепутать
точки/подчёркивания или сократить имя, а с числовыми индексами в
списке, который она только что видела, всё стабильно. Полные
метаданные мы восстанавливаем сами по индексу.

### 5.7. SQLite для метаданных репо

Вектора живут в ChromaDB, но метаданные (имя репо, timestamp,
counts, граф, summaries) хранятся отдельно в `repos.sqlite3`. Можно
было JSON-файлом, но SQLite даёт атомарность записи и нормальный
lookup по id за O(log n), без переписывания всего файла на каждое
изменение. Stdlib, без новых зависимостей.

## 6. Реализация по слоям

### `src/core/`
- `models.py` — pydantic-модели (контракт).
- `config.py` — Settings из env.
- `repo_store.py` — sqlite-обёртка с одной таблицей `repos`,
  атомарным upsert.
- `repo_service.py` — фасад, единственный API для верхних слоёв
  (REST + MCP). Оркеструет ingestion → parsing → indexing → summarisation
  → persistence.

### `src/ingestion/loader.py`
Три entry-point'а: `load_from_directory`, `load_from_zip`,
`load_from_git`. Защита от zip-slip; shallow git clone (`depth=1`);
капы по размеру и числу файлов.

### `src/parsing/`
- `python_parser.py` — AST → Module. SyntaxError возвращает `None`
  вместо raise, чтобы не валить весь батч.
- `dependency_graph.py` — adjacency list, walk-up по точкам для
  резолва вложенных импортов.

### `src/indexing/`
- `chunker.py` — `Module` → list[CodeChunk] (4 типа чанков).
  Deterministic `chunk_id` для idempotent re-indexing.
- `embedder.py` — ленивая обёртка над sentence-transformers.
- `vector_store.py` — ленивая обёртка над ChromaDB. Метод
  `delete_repo(repo_id)` для cleanup.
- `pipeline.py` — `index_repo(modules_with_source, repo_id)`.

### `src/llm/`
- `client.py` — `LLMClient` с ленивой инициализацией, ретраями на
  rate-limit, `LLMConfigError` если нет API ключа.
- `prompts.py` — централизованные prompt'ы. JSON-only output.
- `summarizer.py` — отправляет сигнатуры и docstrings (НЕ тела
  функций — экономит токены), парсит JSON, graceful degradation.

### `src/qa/`
- `retriever.py` — `embed(question)` → `vector_store.query`.
- `rag.py` — формирует пронумерованный prompt-блок, вызывает LLM,
  парсит индексы, собирает `QAResponse` с `QASource`-citations.
  Snippet'ы обрезаются до 800 символов чтобы API-ответ не разбухал.

### `src/api/`
FastAPI, 9 эндпоинтов. `RepoService` инжектируется через
`Depends(get_repo_service)` — это позволяет тестам подменять сервис
без monkey-patching. Доменные ошибки маппятся в HTTP через единый
exception handler.

### `src/mcp_server/`
- `tools.py` — синхронная логика 7 инструментов (тестируется без
  async/MCP runtime). Ошибки рендерятся как `{"error": "..."}` JSON.
- `server.py` — тонкая async-обёртка над `mcp.server.Server`,
  stdio-транспорт, для подключения в Claude Desktop.

## 7. Тестирование

- **117 тестов**, pytest. 1 skip (test_vector_store, требует chromadb).
- LLM, embedder и vector store везде мокаются — тесты офлайн,
  детерминированные, не требуют API-ключа, идут за < 0.5 секунды.
- Покрытие по основным модулям: unit-тесты для каждого слоя плюс
  integration-тест полного пайплайна (`test_repo_service.py:
  test_index_from_directory` гонит весь поток на синтетическом репо

- API-тесты через `fastapi.testclient.TestClient` с FastAPI
  dependency override, проверяют статусы, схемы, /openapi.json.
- MCP-тесты вызывают `dispatch_tool` напрямую — async-обвязка
  адаптерная и не тестируется отдельно.

## 8. Метрики

Замеры на `examples/demo_repo` (5 модулей, ~150 LOC) — см.
`docs/metrics.md` после прогона `python -m scripts.benchmark`:

- **Index time**: ~2-5 с (первый запуск включает warmup эмбеддера).
- **Vector store on disk**: 50-200 KB.
- **`ask` latency**: 1-3 с медиана (LLM-bound — зависит от latency
  Anthropic API).
- **RAG citation accuracy**: 70-100% на наборе из 10 ground-truth
  вопросов (`examples/qa_groundtruth.json`).

Метрика accuracy сознательно лояльная: «правильно» = ответ цитирует
хотя бы один из ожидаемых модулей. Два разных корректных ответа могут
ссылаться на разные но валидные модули (например, «как создать todo»
может приземлиться и в `service.py`, и в `models.py`).

## 9. Выводы

Построен сервис из 5 слоёв + 2 интерфейсов общим объёмом ~2500 строк
production-кода + ~1500 строк тестов. 117 тестов проходят, покрыты все
ключевые сценарии и граничные случаи.

Демонстрируется end-to-end сценарий: дать сервису незнакомый репо,
проиндексировать, получить осмысленные ответы с цитатами на
конкретные функции. Архитектура слоистая, каждый слой имеет узкий
контракт, что позволяет (а) тестировать независимо, (б) расширять
без переписывания (например, добавить JS-парсер).
